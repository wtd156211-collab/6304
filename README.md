# 状态可达性与死锁检测（从 0 实现）

本目录是起始环境：只有规格、现场记录和样例，没有任何代码。请从 0 实现下面这套分析工具，把“靠人看图”的迁移表评审换成逐行可核对的结果。

## 一、范围

要做的事：

1. 实现 Python 包 `stateaudit`（Python 3.13+，仅标准库），入口命令 `python -m stateaudit [--machines samples/machines] [--out var]`，在仓库根目录执行（本机的 Python 在 WSL 里，用 `wsl -- python3 -m stateaudit …`）。
2. 读出目录里每台状态机的迁移表与初始状态集合，按第二、三节的口径算出可达性与问题清单。
3. 产出 `report.json`、每台机器两个逐行文本文件、一份用 `file://` 打开就能看的 `report.html`。

明确不做：

- 不做条件求值：条件只是字符串标签，没有谓词、时序、概率、优先级语义。
- 不读 TSV 以外的格式，不写回、不重排 `samples/` 下的文件。
- 不做图形渲染或编辑器，不起本地服务、不发网络请求，不需要构建步骤。
- 不引入第三方依赖；发现问题不改变退出码。

## 二、口径与公式

设状态集合 V、迁移行集合 E（一行 `u→v` 贡献一条有向边，条件不参与判定）、初始状态集合 I。

- **可达**：`s ∈ R ⟺ 存在 i ∈ I 与 i →* s 的路径`（长度 0 也算）。
- **带条件的迁移**一律视为可发生；**自环**算一条边、计入出度，但不扩张 R。
- **出度** `outdeg(s)`：以 s 为当前状态的迁移行数，自环与完全重复的行都计入。
- **强连通块（SCC）**：极大强连通状态集；块 C 是**汇块** ⟺ 不存在 `u ∈ C`、`v ∉ C` 的边 `u→v`。
- **死循环块（TRAP）**：可达汇块 C，且 `|C| ≥ 2` 或 C 内有自环。含义：进了 C 就再也到不了 C 以外的任何状态。
- **终止状态（TERMINAL）**：可达且 `outdeg = 0`。
- **冲突迁移（CONFLICT）**：存在状态 u 与条件 c，使 `{v | (u,c,v) ∈ E}` 去重后 ≥ 2 个目标。
- **不可达状态（UNREACHABLE）**：`V \ R` 中的状态。

两点补充：UNREACHABLE 覆盖所有不可达状态（含不可达的环）；TRAP、TERMINAL 只报可达块/状态，不与它重复。完全相同的重复行不影响任何结论，也不算冲突。

## 三、状态机与数据结构

一台状态机 = 一张迁移表 + 一个初始状态集合；状态名区分大小写，不做别名与大小写归一。

**状态的规范顺序**（所有输出按它排）：先按 `.init` 行序，再按迁移表数据行序（每行先记「当前状态」、后记「目标状态」），只记首次出现。

内部结构不限；建议映射成 `0..n-1` 下标 + 邻接表，迁移行保留原始行号（冲突排序要用）。

## 四、输入输出与文件格式

### 输入 `samples/machines/`

- `<机名>.tsv`：UTF-8（允许 BOM 与 CRLF），制表符分隔，固定 3 列，第一个有效行是表头 `当前状态\t条件\t目标状态`。
- 解析时忽略空行与以 `#` 开头的行（允许前导空格）；数据行必须正好 3 列，每列 trim 后非空。
- 状态名、条件名不得含空白字符与半角逗号 `,`，不得等于 `->`。
- `<机名>.init`：每行一个初始状态，去重并保持行序，至少 1 个；允许只在这里出现、迁移表里没有的状态。
- `.tsv` 与 `.init` 必须一一配对；目录里没有任何 `.tsv` 也算错误。
- 任何校验失败：把机名与行号写进 stderr，退出码 2，不产出半成品结果。

### 输出（默认 `var/`）

- `var/<机名>.reachability.txt`：每行 `<状态>\t<可达|不可达>`，按规范顺序；UTF-8 无 BOM、LF，每行以换行结尾。
- `var/<机名>.problems.txt`：每行一条问题（格式见下），无问题时是 0 字节文件。
- `var/report.json`：`{"machines":[{"name":…,"states":[…],"reachable":[…],"problems":[…]}]}`；机器按机名 Unicode 码点升序，`reachable` 与 `states` 同序，内容必须与上面两个文本文件一致（排版不限）。
- `var/report.html`：单文件自包含（内联数据与样式），用原生 ES module（`<script type="module">`）渲染；不引用任何外部资源，`file://` 直接打开即可看到每台机器的状态表（状态 + 可达性，同规范顺序）和问题清单（同 `problems`），机器顺序同 `report.json`。
- stdout 每台机器一行 `<机名>\t状态=<n>\t可达=<r>\t问题=<p>`；全部成功退出码 0。

### 问题行格式与顺序（顺序敏感）

类型顺序固定为 `UNREACHABLE` → `TRAP` → `CONFLICT` → `TERMINAL`：

- `UNREACHABLE <状态>`：按规范顺序。
- `TRAP <状态>,<状态>,…`：块内状态按规范顺序、用半角逗号连接；块之间按块内最早状态在规范顺序中的位置排。
- `CONFLICT <状态> <条件> -> <目标>,<目标>,…`：目标去重后按首次出现顺序；先按状态规范顺序，同一状态内按条件首次出现的行序。
- `TERMINAL <状态>`：按规范顺序。

## 五、性能与验收口径

单机上限 20,000 个状态、100,000 行迁移；该规模下全流程（含 HTML）≤ 5 秒、内存 ≤ 512 MB；算法用 O(V+E) 的遍历与 SCC，20,000 长的链不得触发递归崩溃。

验收：

1. `python -m stateaudit --machines samples/machines --out var` 退出码 0，stdout 六台机器各一行。
2. 六台机器逐一比对：`diff samples/expected/<机名>.reachability.txt var/<机名>.reachability.txt` 与 `diff samples/expected/<机名>.problems.txt var/<机名>.problems.txt` 均无差异（逐字节）。
3. `report.json` 里每台机器的 `states` / `reachable` / `problems` 与上述文本一致。
4. `report.html` 用浏览器 `file://` 打开：六台机器齐全，状态顺序、问题顺序同文本，页面不引用外部资源。
5. 只用标准库；`samples/` 保持原样。

## 六、样例说明

`samples/machines/` 六台机器，`samples/expected/<机名>.reachability.txt` 与 `<机名>.problems.txt` 是逐行期望：

| 机名 | 覆盖场景 | 期望要点 |
| --- | --- | --- |
| `order_flow` | 正常机 | 6 个状态全部可达；3 个终止状态；无缺陷 |
| `unreachable` | 含不可达状态 | 3 个不可达（其中一对互指成环）；不可达的环不报 TRAP |
| `stuck_zone` | 含出不去的子图 | TRAP 命中 3 个状态；另有 1 个正常终止状态 |
| `conflict` | 同条件多目标 | 2 处 CONFLICT；同目标重复行不算冲突 |
| `selfloops` | 大量自环、双初始状态 | 50 行自环；带出口的自环不死锁，只有自环的状态报 TRAP |
| `retry_cycle` | 循环结构 | 带出口的重试环不报 TRAP；2 个终止状态 |

`samples/notes.md` 是现场记录，说明这道题要治的两起事故。
